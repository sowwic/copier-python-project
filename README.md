# copier-python-project

Copier template for a Python project: a plain library, a Qt (PySide6) widgets application or a QML application.

## Use

```sh
uvx copier copy --trust gh:sowwic/copier-python-project path/to/new-project
```

`--trust` lets Copier run the one post-generation task (`uv lock`, which creates the lockfile CI needs).
Without it the project is generated and you run `uv lock` yourself.

## What you get

- `src/<package>/`, tests, docs (mkdocs), ruff, `uv`, a `Makefile` (`make check`, `make pytest`, `make release` ...).
- GitHub workflows for tests, code quality, docs and releases (optional).
- Qt projects: resources (`.qrc`, `make qrc`), offscreen Qt CI, `pytest-qt`; QML projects add a `qml/` folder and a qmlls config script.
- Optional PyPI publishing (`make pypi-publish`, `make pypi-publish-dev`).
- Optional PyInstaller bundling (`make bundle`) and a macOS `.app` (`make iconset`, `make install`).

## Makefile

The generated `Makefile` is short: it sets a few variables and includes shared modules from
[`sowwic/makefiles`](https://github.com/sowwic/makefiles) (`general/python`, plus `general/qt`, `general/qml`, `general/bundle` and `general/macos-app` for the project type, and `general/pypi` when publishing to PyPI), which it fetches into `.make/`
(commit that folder, CI and offline work then need no network). `make update-make` fetches them again, at the
`MAKEFILES_REF` pinned at the top of the Makefile; bump the pin to take a newer version. The post-generation task
fetches the modules too, so a new project is ready to commit. Add your own targets below the `include`, or add
steps to a shared one with a double-colon rule (`check::`); the variables a module reads are listed in its README.

## Questions

| Question | Meaning |
| --- | --- |
| `project_name`, `project_slug` | Human readable name, and the repo/distribution name |
| `package_name`, `package_slug` | Importable package under `src/` (the slug must be a valid identifier) |
| `initial_version` | Written to `VERSION`, `pyproject.toml` and `CHANGELOG.rst` |
| `python_version` | Minimum Python version (`requires-python` and the CI version) |
| `author`, `author_email`, `github_user` | `pyproject.toml`, `LICENSE`, README badges and links |
| `github_workflow` | Include the GitHub Actions workflows from `sowwic/gh-workflows` |
| `release_branch`, `develop_branch` | Used by CI, docs deploy and `make release` |
| `publish_to_pypi`, `pypi_name` | Add `make pypi-publish` (PyPI) and `make pypi-publish-dev` (TestPyPI), project URLs, and the name on PyPI |
| `ide` | Neovim, VS Code, Zed (Qt projects only) or none |
| `project_type` | `library`, `qt_app` or `qml_app` |
| `bundle_app`, `macos_app` | Qt/QML only: PyInstaller bundle, macOS `.app` |

## Updating a project

Every generated project holds a `.copier-answers.yml`. When this template improves, bring the changes into
the project (clean git tree first):

```sh
cd path/to/project
uvx copier update --trust
```

Copier re-renders the template at the old and the new version and applies the difference to your project;
where you changed the same lines you get conflict markers to resolve. The template is versioned by git tags
(`v<major>.<minor>.<patch>`): `copier update` moves to the latest tag, `--vcs-ref=HEAD` takes the latest commit.

To adopt a project that was not generated by this template, run `copier copy` over it on a branch, keep the
changes you want from the diff and commit the new `.copier-answers.yml`.

## Developing the template

```sh
uv sync
uv run pytest      # generates the template with several answers and checks the result
```

The files of the generated project live in `template/`; files with Jinja in them end in `.jinja`, the rest is
copied as it is. Conditional files and folders have an `{% if ... %}` in their name. Release by tagging:
`git tag v0.1.1 && git push --tags`.
